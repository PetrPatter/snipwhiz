# Snipwhiz Editor Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A capture opens in an editor. Objects can be drawn, selected, restyled, moved, resized, rotated, undone and redone. Closing saves without asking. The library tile, preview and clipboard all show the annotated result. Re-opening restores every object still editable.

**Architecture:** Pure WPF. The scene graph is one `DrawingVisual` per annotation inside a `VisualCollection` host — no custom panel, no element-per-object. `Annotation.Render(DrawingContext)` lives in `Snipwhiz.Core` and is called by *both* the on-screen canvas and the flattener, which is what makes WYSIWYG a property rather than a hope. Geometry is stored in image-pixel space; a single `ScaleTransform` handles zoom. Undo holds command deltas, never bitmaps.

**Tech Stack:** .NET 10 · WPF (Core **and** App) + WinForms (`NotifyIcon`) · `Microsoft.Windows.CsWin32` · `Microsoft.Data.Sqlite` · `System.Drawing.Common` · xUnit

**Spec:** `docs/superpowers/specs/2026-07-27-editor-design.md` — read §1, §4.1, §4.13 and §7 before starting.

## Scope of this document

Spec 2b delivers in six phases (spec §8). **Phase A is specified here task-by-task.** Phases B–F are listed at task-title granularity at the end and get expanded when reached — later phases depend on what Phase A actually reveals, and writing forty speculative task bodies now would be fiction with checkboxes.

## Global Constraints

Every task's requirements implicitly include this section.

- **Spec 1's and spec 2a's Global Constraints still apply**, with one exception below. Platform floor Windows 11 22H2 / `net10.0-windows10.0.22621.0`; product name `Snipwhiz`; data path `%LOCALAPPDATA%\Snipwhiz\`; balloons not toasts; `TreatWarningsAsErrors`.
- **REVERSED: `Snipwhiz.Core` now references WPF.** Spec 2a's plan said "Core has no WPF reference and does not gain one." Spec 2b §1 supersedes that deliberately — `Render` must be shared by canvas and flattener. Core gains `UseWPF`; Core tests gain an STA runner. **This is the only reversal; every other constraint stands.**
- **Zero new third-party dependencies.** Everything is BCL, WPF, `System.Drawing.Common` or `Microsoft.Data.Sqlite`. If a task appears to need a NuGet package, stop and report rather than adding one.
- **SQLite is touched only from the UI thread.** Unchanged from 2a. The save pipeline flattens on a background STA thread and marshals back for the DB write.
- **Saved PNGs are never modified or rewritten.** The capture is immutable forever. Edits produce `projects/` and `flat/` files; deletion is still the only operation that touches an original.
- **There is exactly one copy-to-clipboard path**, through `ClipboardWriter.Write`. Never `System.Windows.Clipboard.SetImage`.
- **Every consumer resolves a capture through `CaptureAssets`** (spec §4.1). No new call site may reach for `store.ResolvePath` to decide what to *show*. Only the editor's source bitmap uses the original.
- **There is no dirty state.** Do not add an `IsDirty` flag, a save prompt, or a "discard changes" path. If a task seems to need one, the design has drifted — stop and report.
- **A guard must be observed failing before it is trusted.** Where a task names a negative control, run it, watch it fail, and put the failing output in the report. A check that has only ever passed is not evidence.
- **Automated gates must move the way a user moves.** Spec 2a's sweep scrolled one direction and never resized, and passed two UI regressions cleanly. Any new gate states, in its own report, what class of bug it is blind to.

## Phase A — Foundation

### Task 1: Core gains WPF, and an STA test runner

Spec §1. First because every later Core task needs `DrawingContext`, and because if this is awkward it is better to know on day one than at task 6.

**Files:**
- Modify: `src/Snipwhiz.Core/Snipwhiz.Core.csproj`
- Create: `tests/Snipwhiz.Core.Tests/StaFact.cs`

**Interfaces:**
- Produces: Core able to reference `System.Windows.Media`; `[StaFact]` for tests needing the WPF render stack.

- [x] **Step 1: Add `UseWPF`**

Add `<UseWPF>true</UseWPF>` alongside the existing `<UseWindowsForms>true</UseWindowsForms>`. Both can coexist; WinForms is there for `NotifyIcon` and stays.

**Found:** `UseWPF` **removes `System.IO` from the implicit usings**, because `System.Windows.Shapes.Path` collides with `System.IO.Path`. 43 compile errors across `CaptureStore`, `Settings` and `ThumbnailCache`. The merged WinForms+WPF implicit set this project actually gets does *not* include `System.Windows.Shapes`, so nothing here collides and `<Using Include="System.IO" />` restores the SDK default — one line instead of a `using` in every file that touches a path. If a future file does pull in `System.Windows.Shapes`, `Path` becomes ambiguous and that surfaces as a compile error, not a silent change.

- [x] **Step 2: Write `StaFact`** → **delivered as `Sta.Run`, not an attribute**

`RenderTargetBitmap` and `DrawingVisual` require an STA thread. `ClipboardFormatTests` already spins one by hand — generalise it so tasks 6 and 15 do not each reinvent it.

**Deviation:** a real `[StaFact]` attribute needs either the `Xunit.StaFact` package — forbidden by Global Constraints — or a custom xUnit test framework, a few hundred lines to save one call per test. Delivered as `tests/Snipwhiz.Core.Tests/Sta.cs`, a static helper. `ClipboardFormatTests` now uses it.

One behaviour change while generalising: the original ignored `Thread.Join`'s return value, so a deadlocked STA thread returned the default result and the test **passed**. `Sta.Run` throws on timeout.

- [x] **Step 3: Prove it**

`WpfInCoreTests` builds a `DrawingVisual`, draws a filled red rect, renders to a 4×4 `RenderTargetBitmap` and asserts the pixel. An empty render leaves the buffer zeroed, so the red channel distinguishes "drew" from "did nothing".

**Verification — done.** Build clean, 0 warnings with `TreatWarningsAsErrors` on. 105 tests pass (104 existing + 1 new). CsWin32 generation unaffected. App launches and stays up.

**Outstanding for the user:** confirm the tray icon, its menu, and the capture hotkeys still work at runtime — a build cannot show that, and `UseWPF` changes what the process loads at startup.

### Task 3: `CaptureAssets` — the single display path

Spec §4.1. **This is the fix for the review's highest-severity finding** and it lands before anything can write a flat render, so no consumer is ever written against the old assumption.

**Files:**
- Create: `src/Snipwhiz.Core/Storage/CaptureAssets.cs`
- Modify: `ThumbnailCache.cs`, `src/Snipwhiz.App/Library/ClipboardCopier.cs`, `PreviewView.xaml.cs`, `LibraryWindow.xaml.cs`
- Test: `tests/Snipwhiz.Core.Tests/Storage/CaptureAssetsTests.cs`

**The existing problem.** Three call sites independently resolve a capture, and all three take the original: `ThumbnailCache.Generate`, `ClipboardCopier.cs:27`, `PreviewView.xaml.cs:74`. Redirecting only the thumbnail — which is what rev. 1 of the spec did — ships a grid showing the annotated image while preview and clipboard hand back the un-annotated one.

- [x] **Step 1: Write `CaptureAssets`**

`Display` uses `record.FlatPath` as the authority on whether a render was ever saved — no second source of truth, and no directory probing for unedited captures, which is the overwhelming majority. The existence check applies only to captures claiming a render, so a deleted or half-written flat file degrades to the original.

`All` deliberately resolves project and flat from the **id**, not the columns: a save that crashed between writing `flat/<id>.png` and recording it leaves a file no row references, and resolving from columns would orphan it forever.

Also removed a duplicate of the thumbs layout from `ThumbnailCache`, which had its own `ThumbsDir`.

- [x] **Step 2: Route the consumers through `Display`**

Three, not five: **Reveal-in-Explorer and Open-with-default-viewer do not exist.** Spec 2a §2 listed them as in-scope but there is no `Process.Start` anywhere in `Snipwhiz.App`. Noted rather than built — adding them is not this task.

- [x] **Step 3: Tests**

Six, none of which need a database. Includes one asserting an unedited capture resolves **without touching the disk**, and one asserting `All` names an orphaned render the columns never recorded.

**Verification — done, both directions.** `SNIPWHIZ_SEED_EDITED=n` was added to `LibrarySeed` to fake an editor save on the newest n captures, writing a garish magenta render and recording it with `SetEditPaths`. There is no editor yet, and this is the only way to check the routing before one exists to blame.

| Scenario | Result |
|---|---|
| Renders present | exactly 3 of 12 thumbnails magenta — the edited ones |
| Renders deleted, rows still claim them | 0 magenta, **0 broken** — clean fallback |

Thumbnail results measured on disk by sampling centre pixels. Preview and clipboard confirmed by eye against the same seeded library: magenta tile → magenta preview → magenta paste into Paint.

### Task 4: Transforms and hit-testing, unit-tested before any UI

Spec §4.4, §4.6, risk 4. Rotated hit-testing is hand-rolled and easy to get subtly wrong; the maths gets proven against known points while it is still pure functions.

**Files:**
- Create: `src/Snipwhiz.Core/Annotations/Transform2D.cs`, `Style.cs`, `Annotation.cs`, `RectangleAnnotation.cs`
- Test: `tests/Snipwhiz.Core.Tests/Annotations/TransformTests.cs`, `HitTestTests.cs`

- [x] **Step 1: ~~`Transform2D`~~ — dropped, WPF's `Matrix` already is one**

`System.Windows.Media.Matrix` is an affine 2D transform with `Invert`, `Multiply` and `Transform(Point)`, and Core references WPF as of task 1. Writing our own would re-implement tested platform code, and it serialises as the six numbers spec §4.11 already specifies.

This also sharpened the tests: Microsoft's matrix maths is not what can be wrong — *our use of it* is. So the tests moved onto `Annotation.HitTest`.

- [x] **Step 2: `AnnotationStyle` as a record of `Color` and numbers**

Named `AnnotationStyle`, not `Style`: `System.Windows.Style` is imported by every WPF file, and shadowing it would be a permanent papercut across the ~15 annotation types still to come.

- [x] **Step 3: `Annotation` base and `RectangleAnnotation`**

Two invariants worth knowing, both documented at their definitions:

- **Transform carries rotation and translation only, never scale.** Resizing edits the object's geometry, which keeps a stroke the width the user chose, and keeps the transform a rigid motion so a hit tolerance means the same distance in both spaces.
- **Local geometry is centred on the origin**, so rotation turns an object about its own middle with no correction term.

- [x] **Step 4: Hit-test tests, rotated**

**Verification — done, and it caught a flaw in the test itself.** Both wrong implementations were built and run:

| Negative control | Caught by the headline test? |
|---|---|
| Test `Bounds` instead of the inverse transform | yes |
| Apply the transform instead of its inverse | **no — originally missed** |

The first version used a square at 45°, where rotating the probe the wrong way lands it symmetrically outside, so it missed the inverse bug entirely while looking like it discriminated. Replaced with a 200×60 rectangle at 30° and a probe at `R(-30°)·(95,0)`, which separates all three outcomes: correct misses, forgot-to-invert hits, bounds-check hits. Both controls now fail it.

124 tests pass.

### Task 6: The flattener

Spec §4.12. Needs `[StaFact]` from task 1.

**Files:**
- Create: `src/Snipwhiz.Core/Imaging/Flattener.cs`
- Test: `tests/Snipwhiz.Core.Tests/Imaging/FlattenerTests.cs`

- [x] **Step 1: Render a `SceneDocument` over a source bitmap to a `RenderTargetBitmap` at image scale, encode PNG, write atomically.**

Uses WPF's `PngBitmapEncoder`, **not** the project's own `PngEncoder`. `RenderTargetBitmap` only produces `Pbgra32` — premultiplied — and `PngEncoder` takes straight BGRA. Today the canvas is opaque throughout so the two agree, which is exactly what makes it a trap: it would start being wrong the first time an annotation had partial alpha at the image edge.

Crop is clamped to the capture and never empty. Both a crop reaching outside the source and a zero-width one are reachable from a hand-edited project, and the second throws inside `RenderTargetBitmap`.

- [x] **Step 2: Tests against known scenes** — 11 of them, covering placement, z-order vs list order, rotation agreeing with hit-testing, crop offset and clamping, and save round-tripping through a real PNG.

**Verification — done, both controls seen failing, and the second exposed a weak test.**

| Control | Result |
|---|---|
| Annotations never rendered | 6 tests fail |
| Crop offset dropped | 1 test fail → **2 after strengthening** |

`An_annotation_outside_the_crop_does_not_appear` originally sampled pixels where the un-offset rectangle would not have landed anyway, so it passed against the bug it was named for. It now samples `(10,10)` — exactly where the annotation appears if image coordinates are read as output coordinates.

### Task 7: Undo stack and commands

Spec §4.7.

**Files:**
- Create: `src/Snipwhiz.Core/Scene/UndoStack.cs`, `Commands/*.cs`
- Test: `tests/Snipwhiz.Core.Tests/Scene/UndoCommandTests.cs`

- [x] **Step 1: `ISceneCommand` with `Do`/`Undo` holding deltas only** — no bitmaps, ever.

- [x] **Step 2: Six commands, not the five listed**

`Add`, `Remove`, `Move`, **`Reshape`**, `Restyle`, `Reorder`. Reshape is a consequence of task 4: because `Transform` carries no scale, resizing edits the object's own geometry, and undo therefore has to capture geometry. Handled with `CaptureGeometry`/`RestoreGeometry` on `Annotation` so it stays one command rather than one per shape across the fifteen types to come.

- [x] **Step 3: `UndoStack`** bounded at 50 by count, with absorbing.

Absorbing lets a tool apply each step of a drag live — the scene is correct at every frame — while the stack still records one entry. The alternative is every tool buffering its own start state and applying once on release, which is the same logic written once per tool.

- [x] **Step 4: Do/undo/redo identity test per command type**

The harness compares scenes **through the real serializer**, so the check cannot drift from what a save produces, and it covers fields a future annotation type adds without touching the test.

**Verification — done. The harness's own control is now a permanent test.**

| Control | Result |
|---|---|
| A command whose `Undo` is a no-op | harness throws — asserted by `The_round_trip_harness_catches_a_command_that_does_not_undo` |
| Absorbing removed | 3 tests fail |
| Redo branch not discarded on a new action | 1 test fails |

The first is kept as a test rather than run once by hand: a harness that has only ever seen working commands is not known to catch a broken one, and that stays true next month.

### Task 8: `CanvasHost` — the scene graph, and the first pixels

Spec §4.2, §4.3.

**Files:**
- Create: `src/Snipwhiz.App/Editor/CanvasHost.cs`

- [x] **Step 1: `FrameworkElement` over a `ContainerVisual`.** One `DrawingVisual` per annotation, held as children of one container rather than of the element — so the view transform is a single object regardless of how many annotations exist.

- [x] **Step 2: Per-object invalidation** — `Invalidate(annotation)` for appearance, `Rebuild()` for structural change only.

- [x] **Step 3: Zoom and pan** — one matrix on the container; 10%–800%, `Ctrl`+wheel anchored at the cursor, space-drag and middle-drag, fit-on-open that never enlarges. Plain wheel is deliberately left alone: there are no scrollbars, and a bare wheel that zooms surprises anyone who reached for it to scroll.

- [x] **Step 4: Screen ↔ image conversion**, with `ToImageLength` for the perceptual quantities — handle sizes and hit tolerances — that must stay constant on screen.

`HitTest` walks the document rather than using `VisualTreeHelper.HitTest`, because an unfilled shape has no pixels in its middle and clicking there must still select it. `Annotation.HitTest` owns that rule; letting WPF's geometry hit-testing own it would put it in a second place.

**Verification — done, instrumented and with a negative control.** `Diagnostics/CanvasVerification.cs`, gated on `SNIPWHIZ_VERIFY_CANVAS`, drives a 200-object scene and counts renders.

| | positive | `SNIPWHIZ_VERIFY_BREAK_INVALIDATION=1` |
|---|---|---|
| zoom sweep, 20 steps | **0 renders** | 0 renders |
| move one object, 40 steps | **40 renders, 0.5 ms** | **8000 renders, 54.7 ms** |
| structural rebuild | 201 | 201 |

8000 is exactly 40 × 200 — the whole scene redrawn per step, which is what an element-per-object or single-`OnRender` canvas is forced to do. The zoom sweep rendering *nothing* in both is what proves the view transform sits on the container.

**Also removed `System.Drawing` and `System.Windows.Forms` from `Snipwhiz.App`'s implicit usings**, for the same reason as Core in task 4: they shadow `Point`, `Size`, `Color`, `Brush`, `Pen`, `MouseEventArgs`, `MouseButtonEventArgs` and `KeyEventArgs` — every WPF type the editor is built from. `TrayHost` is the only WinForms surface and now says so.

161 tests pass.

### Task 9: Selection, handles and rotate

Spec §4.6.

**Files:**
- Create: `src/Snipwhiz.App/Editor/SelectionAdorner.cs`, `Tools/SelectTool.cs`

- [x] **Step 1: Eight resize handles, one rotate handle, a move region.** Handles are checked before object hit-testing — they sit on the object's edge, so object hit-testing would swallow every one of them.

The overlay renders **outside the view transform**, in element coordinates, so a grab handle is the same size under the mouse at 10% and at 800%.

- [x] **Step 2: Resize maths in Core, unit-tested** — `Annotations/Handles.cs`, not the App. Handle positions, resize with an anchored opposite corner, aspect and centre modifiers, and rotation with snapping are pure geometry, and this is the part that goes wrong.

- [x] **Step 3: Marquee and Shift-click multi-select.** Shift, not Ctrl — Ctrl+click is unclaimed but Ctrl+wheel already means zoom on this surface, and Shift-to-extend matches the marquee's own modifier.

**Reduced, deliberately:** handles show for a *single* selection. A multi-selection can be moved and deleted but not resized or rotated as a group. Eight handles per object is noise that hides the useful gesture, and group transform composition belongs with multi-select restyle in phase E. Flagged rather than silently dropped.

- [x] **Step 4: Shift constrains aspect / 15° rotation; Alt resizes about centre.**

**Verification — the manual check became an automated one.** 20 tests in `HandleTests`, including every one of the eight handles anchoring its opposite corner on a 37°-rotated object, and a `[Theory]` across 30°, 45°, 120° and −70°.

**Negative control:** compute the new centre in image space instead of the object's local frame — the obvious mistake, and *identical* on an unrotated object.

| | result |
|---|---|
| Rotated tests | **6 fail** |
| Unrotated tests | all pass |

That split is the point: the unrotated tests cannot catch this class of bug, so a suite containing only them would have looked complete.

**Also added `ResizeAnnotation`**, a seventh command. A resize changes size *and* transform, and applying `Reshape` plus `Move` per mouse-move would push alternating entries that can never absorb each other — forty moves costing eighty undo steps.

**Verification — done, and the user found a real defect the tests had not.**

**Undo granularity.** Drawing a rectangle, rotating it, then pressing Ctrl+Z deleted the rectangle instead of unrotating it. `AddAnnotation` was absorbing *every* later change to the shape it created, with no boundary — and `MoveAnnotation` had the same flaw, so two separate drags of one object collapsed into a single undo step.

Absorbing is now bounded by a **gesture** rather than by an object: `UndoStack.BeginGesture()`, called on every press and on each discrete action. Arrow-key nudges deliberately do not begin one, so holding an arrow stays a single step. Three tests pin it, including the exact sequence reported.

**Two screens, one window.** The editor became a `UserControl` behind a Library/Edit switch — spec §4.16, superseded during this task. This *replaces* the pull-up sheet rather than deferring it, and removes the phase F hazards the review had flagged.

Confirmed by hand: draw, rotate, undo unrotates; two drags are two steps; screen switch both ways; Escape unwinds selection then screen.

184 tests pass.

### Task 11: The save pipeline

- Modify: `App.xaml.cs`

- [x] **Step 1: Write `.ssproj`, then flatten, on a dedicated STA background thread.**

**Departure from the spec's threading, for a race it did not account for.** The `SceneDocument` lives on the UI thread, so handing it to a background flatten lets `Ctrl+S` render a half-changed scene while the user keeps drawing. The pipeline now **serialises on the UI thread** — a few KB, sub-millisecond, no IO — and hands the background thread a string, which it writes and then **parses back** into an independent object graph to render from. No clone method, no lock on the scene, and the render is provably of exactly what was written.

- [x] **Step 2: Marshal back for the DB update.**
- [x] **Step 3: A failed flatten still commits the project.**
- [x] **Step 4: Raise `Saved(record)`** with the updated record, plus `RenderFailed` for the balloon.

**Verification — done, both paths, and the failure path found a bug.**

### Task 12: Making the library actually refresh

Spec §4.13. **The review's second-highest finding, and the bug the spec itself predicted.**

**Files:**
- Modify: `CaptureTileViewModel.cs`, `LibraryViewModel.cs`, `LibraryWindow.xaml.cs`

**The existing problem, verified in source.** Four mechanisms each independently prevent a refresh: `LibraryViewModel` keeps one view model per capture id forever (`LibraryViewModel.cs:17`); `CaptureTileViewModel` latches `_loaded` and returns early on later binds (`:86`); `InsertNewest` dedupes by id so re-raising the capture event is a no-op; and the decode uses `UriSource` without `IgnoreImageCache` (`:100`), so WPF's global cache can serve a stale bitmap for a path whose contents changed.

- [x] **Step 1: `CaptureTileViewModel.Refresh(updated)`** — clear `Thumbnail`, `IsMissing` and `_loaded`, re-request **only if still bound**, reusing the binding count rather than inventing a second liveness notion.

**A fifth mechanism the plan had not listed.** `ThumbnailCache` resolves through `CaptureAssets.Display`, which chooses between the render and the original by reading `FlatPath` **on the record it is handed** — and the tile holds the record from before the save. Deleting the cached JPEG and re-fetching against the stale record regenerates a thumbnail of the *un-annotated* capture: the same visible failure, reached by a longer route. `Refresh` therefore swaps the record, and `LibraryViewModel.Replace` swaps it in `_records` too, which carries the keyset paging cursor.

- [x] **Step 2: Decode with `BitmapCreateOptions.IgnoreImageCache`.**
- [x] **Step 3: The save pipeline removes the cached JPEG; the library pushes the refresh.**

**Verification — done, three runs, both controls seen failing.**

| Run | thumbnail on disk | tile on screen |
|---|---|---|
| Positive | 601 annotation-red pixels | **updated** |
| `SNIPWHIZ_VERIFY_BREAK_REFRESH=1` | **never regenerated** | stale |
| `SNIPWHIZ_VERIFY_BREAK_IMAGECACHE=1` | **1,072 annotation-red pixels** | stale |

Both controls confirm the save itself worked — project and render on disk either way. Fixing one alone still ships the bug, looking identical to the user.

Control B produced the sharpest evidence: with the cache flag removed the **preview showed the rectangle while the tile did not**, same capture, same moment. `PreviewView` decodes from a `FileStream` and never touches WPF's URI cache; the tile decodes via `UriSource` and does.

**Harness note:** deleting the throwaway library immediately after killing the app leaves `library.db` locked and the capture files gone, so the next run inherits rows pointing at nothing and skips seeding. Every tile then reads "File missing" — which is spec 2a §4.12 behaving correctly, not a defect. Cleanup now waits for process exit.

184 tests pass.
